# Kandev deployment

[中文](README.md) | **English**

Deploys the [multi-agent development workflow](../docs/workflow.en.md) to any Kandev workspace. To have an agent deploy and verify it for you, see [../AGENTS.md](../AGENTS.md) (Chinese).

## Files

| File | Purpose |
|---|---|
| `ma.py` | Entry point: pre-deployment question list, install into a standalone directory, prompt diff, deploy, health check (doctor), upgrade |
| `deploy_questions.json` | What must be confirmed with the user before deploying, customizing or upgrading (view with `ma.py questions`) |
| `build_workflows.py` | The single source of configuration: structure and prompts of the three workflows (rule slots come from `../rules/`), plus the `apply` / `dump` commands |
| `manifest.py`, `slots.py`, `kandev_client.py` | Install manifest and answer validation, rule-slot loading, the Kandev MCP client |
| `check_docs.py` | Self-check: whether prompts.md is up to date, links, step names, template paths, version number, stage regression tests. Run it after changing the workflow and before deploying |
| `stage.py` | Stage classification for the guard: works out from Kandev state whom each task is "waiting on", and generates `agents/guard/stage.md` and alerts |
| `tests/` | Offline tests: regression tests for `stage.py`, install / customize / deploy-gate / upgrade tests for `ma.py` (against an in-memory Kandev stand-in), tests for the management directory tools |
| `verify_export.py` | Exports the deployed workflows, prints each step's configuration for checking, and writes a copy with machine-specific IDs removed to `export/` |
| `export/` | Example workflows: the three workflows exported from a real deployment, see [export/README.en.md](export/README.en.md) |
| `handoff/` | Handoff prompts for work the external MCP cannot do and that must be handed to an agent inside Kandev |
| `profiles.example.json` | Example format for role → agent profile ID |
| `profiles.local.json` | The profile IDs actually used on this machine (written by `ma.py apply` from the recorded answers; not committed, not edited by hand) |
| `kandev_ids.json` | Generated by `apply`: the IDs of each workflow and step (different on every machine, not committed) |

## Prerequisites

- Kandev is running and the external MCP endpoint is reachable (default `http://localhost:38429/mcp`; put a different address in the answers as `kandev_url`).
- Python 3.9+. The scripts use only the standard library; no dependencies to install.
- Agent profiles prepared in Kandev: 5 required roles (pm, auditor, developer, reviewer, mechanical) and 4 optional ones; how to choose them is in "Roles and profiles" in [docs/workflow.en.md](../docs/workflow.en.md). `ma.py install` checks the required roles, defaults and the "must differ" constraints.

## Deployment

Replace `python` with this machine's Python interpreter.

```
python kandev/ma.py questions --stage install          # what to confirm before deploying
python kandev/ma.py install --answers answers.json     # record the answers; a standalone install copies files to <home>
python <home>/kandev/ma.py diff                        # what is in the workspace now, and what would change
python <home>/kandev/ma.py apply                       # self-check → import / update in place → guard handoff file → export
python <home>/kandev/ma.py doctor                      # check the install directory, deployed workflows and the guard
```

The answers file is one JSON object; `ma.py questions` lists the keys. The minimum:

```json
{
  "setup_style": "quick",
  "workspace_id": "<workspace id>",
  "profiles": {"pm": "<profile id>", "auditor": "…", "developer": "…", "reviewer": "…", "mechanical": "…"},
  "guard_automation": "yes"
}
```

With `setup_style` set to `custom`, also give `install_mode`, `home` (not in link mode), `python` and `kandev_url`. `install` lists every problem and refuses to run when a must-ask item is missing, a key is unknown, the profiles break a constraint, or a path contains spaces.

- **Two install modes** (`install_mode`): `standalone` (default) copies everything needed at run time into the install directory `<home>` (default `~/.kandev-ma/<first 8 chars of the workspace id>/`); every path written into Kandev points there, so deleting this repository afterwards does not break anything. `link` copies nothing and `<home>` is this repository, for people who change the workflow itself. In link mode one repository can be deployed to several workspaces; later workspaces get ids and heartbeat files named with the first 8 characters of their id.
- **When `apply` finds workflows with the same name**:
  - Same series (same major.minor, e.g. v3.3 and v3.3.4): prompts, profiles, description and step structure are updated in place; step IDs and tasks are kept. It requires `--confirmed <value printed by ma.py diff>`, and `--with-running` when projects are in progress.
  - Another series: it requires `--retire`. The old version is renamed "<name> (<old version>)" with all its tasks, then the new version is imported. Projects in progress finish on the old workflows, but the guard no longer patrols them.
- **Customizing**: rule slots are described in [../rules/README.md](../rules/README.md) (Chinese); overrides go in `<home>/custom/rules/`, then `diff` + `apply` again.
- **Upgrading**: in the new repository run `python kandev/ma.py upgrade --home <home>` (`--dry-run` first), then `diff` + `apply` in `<home>`.
- **Changing an answer**: `ma.py answer --set key=value` (profiles, guard_automation, python, kandev_url, setup_style; to change the workspace or install mode, install again).
- After deploying, check it against "Verify the deployment" (验收部署, section B) in [AGENTS.md](../AGENTS.md).

Internals: `ma.py apply` calls `build_workflows.py apply`, which imports in the order W3 → W2 → W1 (each later workflow's prompts embed the step IDs of the earlier one), first without profiles, then binds profiles step by step by ID, and finally writes the ids file.

## Guard automation

The external MCP cannot create automations, so the guard (one per workspace, covering all projects) has to be created by an agent inside Kandev:

1. `ma.py apply` (or `ma.py guard`) writes two files under `handoff/`: `guard-handoff.<first 8 chars of the workspace id>.local.md`, a copy of [handoff/guard-automation.md](handoff/guard-automation.md) (Chinese) with this machine's values filled in, and `guard-prompt.<first 8 chars>.local.md`, the full guard prompt.
2. In any Kandev task, give the whole "handoff prompt" (交接 prompt) section of the handoff file to the agent to execute.

You can also create it manually in Kandev Settings → Automations: schedule `*/20 * * * *`, hidden run, a profile with a cheap model, concurrency 1; for the prompt use the full text in the code block of `guard-prompt.<first 8 chars>.local.md`.

To see what the guard would see: `python <home>/kandev/stage.py --ids <ids file> --dry-run`. A run without `--dry-run` records this run's alerts as sent.
