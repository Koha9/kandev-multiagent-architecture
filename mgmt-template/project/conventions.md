# 协作规范 · <project>

> 写者：pm。代码风格等通用规范以仓库内的 `AGENTS.md` 为准，这里只记录**多 agent 协作**相关的约定。

## 分支
- 基线分支：`<main>`
- 模块分支：`mod/<模块>`，从基线切出，经集成分支合回基线
- 开发分支：由 Kandev worktree 自动命名，从模块分支切出，合回模块分支
- 集成分支：`integration`，由结合测试模块在规划时建立（没有该模块时在项目验收时建立），合并所有模块分支；用户终审通过后由「收尾合并」步骤合入基线分支

## 提交
- commit message 以任务 id 开头：`auth-02: 实现令牌刷新`
- 一个任务的提交只改该任务 `owns` 内的路径

## 测试
- 每个任务的契约必须写明可直接执行的测试命令
- 新功能必须带测试；不能为了通过而删除或弱化已有测试
- 结合测试（integration-test 模块）：对真实组装的应用运行，断言用户可见的结果和数据状态，只 mock 消耗额度的外部调用；优先用自动化工具，手动操作只作回退
- 结合测试测出产品缺陷时保留失败的用例并上报缺陷，不改断言、不加 mock、不跳过；修复由 integration-test 模块建子任务完成

## 接口
- 任务之间、模块之间只通过 `modules/<模块>/interfaces.md` 中的接口互相依赖
- 状态为"冻结"的接口要变更时：模块内由模块 agent 决定；跨模块必须升级给 pm 并写 ADR

## 消耗额度与外部副作用
- 真实 AI / 付费 API 调用、部署、推送远端、改远端设置：必须由显式开关打开（例如环境变量 `<PROJECT>_REAL_AI=1`），默认关闭
- 需要真实调用的测试用 marker 标记，并且在 conftest（或同等位置）检查开关，未打开时一律 skip。只靠测试配置默认值不够
- 审核、验收复跑测试时按 environment.md 原样执行，不得修改测试选择参数（`-o addopts`、`-m`、`-k` 等）
- 每种真实调用的次数上限：<按项目填写，例如每种接入 ≤2 次>

## 结果与状态
- 验收类结论（PA、MA、AC）只用 `pass` / `fail` / `unverified(原因)`。没有亲自验证的不写 pass；unverified 不算 fail，但必须登记到 `attention.md`「无法验证的项」
- 任务 report：`done`（全部 AC 实现并通过）、`blocked`（做不完，列出 remaining）、`dropped`（无需改动，附证据，由模块 agent 确认）
- 模块 REPORT：`done`、`partial`（有 unverified 或剩余项，逐条列出）、`failed`
- 有界面改动的任务（`ui: true`）：report 附截图（改的是已有界面时要有改动前和改动后），存到 `<mgmt_root>/evidence/<任务id>/`

## 管理目录与记录
- 管理目录如果是 git 仓库：只 `git add` 自己担当的路径，禁止 `git add -A` / `git add .`；提交时设置 `MGMT_SCOPE=<scope>`
- 时间戳一律取自系统时钟（`Get-Date -Format "yyyy-MM-dd HH:mm"` / `date '+%F %R'`）
- 临时目录、worktree、后台进程、端口：登记到自己的 NOW「注意」节，用完清理；留给终审的写进 final-report「临时资源」

## 禁止
- 修改 `owns` 范围以外的文件
- 替别人查询：不归你担当的信息，去问担当者
- 在 GitHub 评论里进行 agent 之间的对话
- 在消息或文档中写入密钥
