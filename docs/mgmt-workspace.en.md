# Management workspace structure (compaction-resistant)

[中文](mgmt-workspace.md) | **English**

> Companion to [workflow.en.md](workflow.en.md). Copy-ready templates are in `mgmt-template/`, the message format is in `mgmt-template/protocol/message.md`, and each step's prompt is in [prompts.md](prompts.md) (Chinese).

## 1. Goal

Whenever an agent is compacted, reset or restarted, it must be able to recover the following 4 things in **at most 3 file reads**:

1. Who I am (scope, role)
2. What I am doing (current goal)
3. What to do next
4. Who I am waiting on, and for what

Recovery **does not depend on conversation history**. Conversation history is unreliable after compaction, and expensive to read.

---

## 2. Three hard rules for compaction resistance

| # | Rule | How | Prevents |
|---|---|---|---|
| R1 | **Write before acting** | Before any action with external effects (`create_task`, sending a message, `move_task`, `step_complete`), first register it under NOW's "Unconfirmed intents (未确认的意图)"; after it runs, delete that entry and write a journal line | Not knowing whether an action happened when compaction hits right before or after it |
| R2 | **Persist before every turn ends** | NOW must be refreshed before a turn ends | Compaction loses at most one turn of process, never state |
| R3 | **Recover from files only** | On recovery read only README → role card → your own NOW | Drift from relying on conversation summaries, and repeated investigation |

R1 is backed by **idempotency**:
- `create_task_kandev` always carries an `external_id` (`mod-<module>` for modules, the task ID for development tasks). If recovery finds an unconfirmed create intent, call again with the same `external_id`; no duplicate task is created.
- Messages carry a unique `id`; receivers deduplicate by id.
- Before redoing `move_task_kandev` or `step_complete_kandev`, first confirm which step the task is currently in. This is checking the result of your own action, not "querying others".

---

## 3. Recovery protocol (written into the README and every workflow prompt)

```
1. Confirm your scope and mgmt_root from the [TASK v1] header of the task description
2. Read <mgmt_root>/roles/<role>.md
3. Read your own NOW
   - Management roles: <mgmt_root>/agents/<scope>/NOW.md
   - Developer: Kandev task doc now
   - Reviewer, guard: no NOW, start from scratch (both kinds of work are idempotent by nature)
4. Handle "Unconfirmed intents": redo with the same idempotency key, or delete after confirming it is done
5. Handle "Waiting on": check the conversation for a reply; on timeout, resend or escalate per the message protocol
6. Continue from item 1 of "Next steps"
```

## 4. Directory structure and writers

```
<project>-mgmt/                         kept outside the development worktree
├─ README.md                 map + recovery protocol          PM (rarely changed after init)
├─ roles/                    role cards (full rules)          read-only (copied from template)
│   ├─ pm.md
│   ├─ module.md
│   ├─ developer.md
│   ├─ reviewer.md
│   └─ guard.md
├─ protocol/
│   └─ message.md            message and handoff format       read-only (copied from template)
├─ tools/                    check_owns / quota / mgmt_precommit  read-only (copied from template)
├─ project/
│   ├─ charter.md            verbatim requirements R-n, goals, scope, modules, PA  PM
│   ├─ attention.md          items for the user (with recommended answers)  PM
│   ├─ conventions.md        collaboration conventions, constraint list  PM
│   ├─ environment.md        environment baseline, commands, smoke test  PM
│   ├─ registry.json         ownership registry (who owns what, task ids)  PM
│   ├─ status.json           global status snapshot           PM
│   ├─ final-report.md       project acceptance report        Project acceptance step (auditor); the "收尾" (wrap-up) section is written by the Final merge step
│   └─ decisions/
│       └─ ADR-0001-*.md     cross-module decisions, one file per decision  PM
├─ agents/                   private state of management agents
│   ├─ pm/
│   │   ├─ NOW.md                                             PM
│   │   └─ journal.md                                         PM
│   ├─ mod-<module>/
│   │   ├─ NOW.md                                             that module's agent
│   │   └─ journal.md                                         that module's agent
│   └─ guard/
│       ├─ journal.md                                         guard
│       └─ stage.md          who we are waiting on now        generated by kandev/stage.py (dedup state lives in the architecture repo's kandev/guard_state/)
├─ modules/<module>/
│   ├─ spec.md               module goals + module acceptance criteria  that module's agent
│   ├─ interfaces.md         interface contracts (external + between tasks)  that module's agent
│   ├─ tasks.json            development task list            that module's agent
│   └─ acceptance.md         acceptance records (append-only)  that module's agent
├─ evidence/<task id>/       UI screenshots                   that task's developer
└─ quota/ledger.json         quota ledger                     written only by tools/quota.py
```

Developers and reviewers **do not write to the management directory** (except screenshots in `evidence/<task id>/` and the quota ledger, which scripts write). Their state and deliverables live in **the task docs of their own Kandev task**:

| Task doc | Writer | Readers | Purpose | Template |
|---|---|---|---|---|
| `now` | developer | the developer itself | private checkpoint | `mgmt-template/task-docs/now.md` |
| `report` | developer | reviewer, module agent | reporting contract | `mgmt-template/task-docs/report.md` |
| `review` | reviewer | developer, module agent | review verdict | `mgmt-template/task-docs/review.md` |
| `charter-review` | Plan review (立项评审) (in the pm task) | pm | plan review record | no fixed template: per-item verdicts, blocking issues, suggestions |

The task contract itself lives in the **task description** (the `[TASK v1]` header plus the contract body), written by the creator and read-only afterwards. This way no cross-task doc writes are needed.

**Single-writer rule**: every file has exactly one writer. To change someone else's file, message its owner and let them make the change.

---

## 5. When to write

| When | What to write |
|---|---|
| Entering a step | NOW: step, entry, current goal, next steps |
| Before an external action | Add a line to NOW "Unconfirmed intents" |
| After an external action | Delete that intent; add a journal line |
| Sending a message that needs a reply | Add a line to NOW "Waiting on (等待中)" (register before sending, also under R1) |
| After receiving and handling a message | Add a journal line; change NOW only if the plan changed |
| Before a turn ends | Refresh all of NOW |
| Step ends | Roll results into the corresponding owned files (status.json, tasks.json, acceptance.md); rewrite NOW for the next step |

---

## 6. Size limits (to keep reads fast)

| File | Limit | When exceeded |
|---|---|---|
| README.md | 60 lines | move details into roles or project |
| roles/*.md | 80 lines | — |
| NOW.md / now | 40 lines | delete finished details, keep only pointers |
| journal.md | read only the last 30 lines on recovery | above 200 lines, roll old content into `journal-<n>.md` |
| spec.md / interfaces.md | 150 lines | split files by subdomain |
| ADR | 40 lines | — |
| Message body | 30 lines | use refs pointing to files instead |

## 7. Format conventions

- **Use JSON for state that machines decide on** (registry.json, status.json, tasks.json). Fields are fixed; only "status-type fields" may change (see section 8). Following Anthropic's experience: models are less prone to mangling JSON than Markdown.
- **Use Markdown with fixed headings for narrative content**. Agents locate content by heading, so **do not rename headings**; write "无" (none) in a section with no content instead of deleting it.
- **Logs are append-only**, one event per line, never edited afterwards: `YYYY-MM-DD HH:MM | type | content | pointer`.
- **Take timestamps from the system clock**; do not infer them.
- **If the management directory is under git, only `git add` paths you own**. The single-writer rule governs files, and `git add -A` would commit other agents' files too. Enforce this with the `tools/mgmt_precommit.py` hook: declare your scope with `MGMT_SCOPE` when committing; out-of-scope files are rejected.
- **Report results truthfully**: acceptance verdicts use only `pass` / `fail` / `unverified(reason)`; partial completion is `partial`.
- **Register temporary resources**: temp directories, worktrees, background processes and ports go into the "Notes (注意)" section of your NOW and are cleaned up after use; anything left for the final review goes into final-report "Temporary resources (临时资源)", to be cleaned up by the Final merge step.
- **Reference by path or ID** (`modules/auth/interfaces.md#login`, `ADR-0003`, `M-mod.auth-261109-102000`), do not copy the original text.
- **Do not record raw code**; record only paths, commands and conclusions.
- Use the time format `YYYY-MM-DD HH:MM` throughout, in the local time zone.

ID rules:

| Object | Format | Example |
|---|---|---|
| scope | `pm` / `mod:<module>` / `dev:<task id>` / `rev:<task id>` / `guard` | `dev:auth-02` |
| module | lowercase English | `auth` |
| development task | `<module>-<two-digit number>` | `auth-02` |
| requirement (verbatim excerpt) | `R-<n>` | `R-4` |
| pending user confirmation / cannot be verified | `Q-<n>` / `U-<n>` | `Q-2` |
| project acceptance criterion | `PA-<n>` | `PA-3` |
| module acceptance criterion | `MA-<n>` | `MA-1` |
| task acceptance criterion | `AC-<n>` | `AC-2` |
| message | `M-<scope with colon replaced by dot>-<YYMMDD-HHMMSS>` | `M-dev.auth-02-261109-142530` |
| ADR | `ADR-<4-digit number>-<short title>` | `ADR-0003-token-format` |

## 8. JSON fields

### registry.json (ownership registry, written by PM)

| Field | Description | Mutable |
|---|---|---|
| `project`, `mgmt_root`, `repo`, `base_branch` | project constants | not changed after init |
| `agents[].scope` | unique identifier | no |
| `agents[].role` | `pm` / `module` / `guard` | no |
| `agents[].kandev_task_id` | filled in after creation | yes |
| `agents[].owns` | ownership scope (files or responsibilities), used for "whom to ask" | requires an ADR |
| `agents[].branch` | module branch | no |
| `agents[].status` | `active` / `done` / `failed` | yes |

Ownership of development tasks is not in the registry; it is recorded in the corresponding module's `tasks.json`.

### status.json (global snapshot, written by PM)

| Field | Description |
|---|---|
| `phase` | `planning` / `baseline` / `dispatch` / `developing` / `project-acceptance` / `final-review` / `done` |
| `modules[]` | `name`, `kandev_task_id`, `status` (`blocked` / `planning` / `developing` / `accepting` / `reported` / `done` / `failed`), `done`, `total`, `last_report` (message id), `blocked_reason` |
| `open_escalations[]` | pending escalations: `msg`, `from`, `topic`, `since` |
| `open_decisions[]` | ADR numbers under discussion |

### tasks.json (module task list, written by the module agent)

| Field | Description | Mutable |
|---|---|---|
| `id`, `title` | task identity | no |
| `owns` | paths this task may modify, i.e. its ownership scope | requires replanning |
| `blocked_by` | prerequisite task ids | requires replanning |
| `acceptance` | AC list, each with `covers: MA-n` | requires replanning, plus an entry in acceptance.md |
| `refs` | requirement sources (R numbers in the charter) | requires replanning |
| `ui` | whether the UI changes; when true the report must include screenshots | requires replanning |
| `kandev_task_id` | filled in after creation | yes |
| `status` | `planned` / `creating` / `held` (waiting on prerequisites in Queued (待开发)) / `todo` / `merged` / `dropped` / `failed` | yes |
| `passes` | set to true by the module agent during module acceptance | yes |
| `review_rounds` | number of review rounds | yes |
| `note` | one-line note | yes |

## 9. Initialization order

1. **The user**: creates the project management task in Kandev, with the `[TASK v1]` header in the task description (including `mgmt_root`, `mgmt_template`, `repo`).
2. **PM (Project planning (立项规划))**: finds that `mgmt_root` does not exist → copies all of `mgmt-template/` → fills in the constants in registry.json and its own task id.
3. **PM (Module dispatch (模块下发))**: adds an entry to registry.json for every module task it creates.
4. **Module agent (Module planning (模块规划))**: copies `agents/_template/` → `agents/mod-<module>/`, and `modules/_template/` → `modules/<module>/`.
5. The template directories `agents/_template/` and `modules/_template/` stay in place unchanged, as the source for later copies.

---

## 10. Design trade-offs

- **Project planning does not use plan mode**: Claude Code's plan mode cannot write files, and Project planning's output is precisely the management files. User review happens in the Plan approval (立项确认) step.
- **Developer and reviewer state lives in Kandev task docs, not the management directory**: the management directory is outside the worktree, and a development agent only needs its own state.
- **Ask whoever owns it**: instead of having agents dig through conversation logs or read code to find answers, they look up the ownership registry and ask the owner directly (see section 1 of `protocol/message.md`).
