## 1. Design principles

1. **Single writer**: for any piece of code or any file, only one agent writes at a time. Parallelism happens only between independent tasks, and each task has its own worktree.
2. **Tests are the referee**: every task has a machine-checkable completion condition (tests, lint, build). An agent's self-assessment does not count.
3. **Reviewers have a clean context**: review, plan review, module acceptance and project acceptance all switch profile and open a new session, and look only at the deliverables and the acceptance criteria. Verifiers do not set their own criteria: they apply the criteria written by the level above, and write every failure as a fix item that can be dispatched as is.
4. **State lives in files; sessions are disposable**: any session can be reset at any time and recovers from the management directory and the task docs (recovery protocol).
5. **Managers do not write code**: the project manager and module managers only plan, delegate and record; even the environment and skeleton are built by the baseline module through development tasks.
6. **Every loop has a cap**: send-backs, review rounds and message rounds all have hard caps; beyond them, the issue goes to the level above or to a human.
7. **Gates live inside the workflow**: when unattended, an independent review step passes the gate in place of a human gate, instead of relying on polling by an external guard.
8. **Operations with side effects are off by default**: operations that consume quota or affect the outside world can only be turned on by an explicit switch; which ones exist and how to turn them on is defined by each project according to the [project conventions](project-conventions.en.md).
9. **Verbatim requirements all the way through**: user requirements are excerpted one by one as R-n, and every PA, MA and AC states which ones it covers; requirements are never rewritten; the implementation approach is left to the level below, and the level above at most attaches suggestions.
10. **Constraints that can be enforced in code are not left only in the prompt**: every constraint is labeled with how it is enforced (enforced in code / check script / prompt only); when blocked by code, stop and report — do not work around it.
11. **Honest conclusions**: an acceptance verdict is only pass / fail / unverified(reason); partial completion is written as partial; if no change is needed it can honestly be dropped. Everything the user needs to handle is collected in one place, each item with a recommended answer.
12. **Hard boundaries, loose approach**: the boundaries (owns, single writer, quota switches, reporting rules) govern *where* an agent may change things, not *how* it does the work. Prompts state only boundaries, deliverables and completion conditions; planning and approach are left to the agent's judgment. Requirements and AC are the floor; do the work well according to their intent. The charter states its reading of the requirements in "Product intent", and contracts state intent.
13. **Split work along knowledge boundaries**: the project level (pm) holds only the verbatim requirements, product intent, the module list, the boundaries between modules (B-n), the project acceptance criteria and decisions; the module level holds its own spec, interfaces, tasks and code, and sees other modules only through their public interfaces; a development task needs only a self-contained contract and its own owns. Long-running sessions (Coordination, Waiting on development) only route; investigation, acceptance and coding happen in one-off sessions whose results are written to files.

## 2. Overall structure

```
Project management task (W1, root task, 1)
 ├─ creates → module management tasks (W2, independent tasks; baseline first, the others blocked_by baseline and able to run in parallel)
 │          └─ subtasks → development tasks (W3, own worktree, base_branch=mod/<module>)
 └─ guard (Kandev automation, scheduled read-only patrol, alerts the upstream manager)
```

- Module tasks are **not nested** under the project task. Subtasks on a regular Kandev board are only one level deep, so modules report to the pm with `message_task_kandev`.
- **Knowledge layers**:

  | Level | Knowledge it holds | Does not touch |
  |---|---|---|
  | Project (pm) | Verbatim requirements, product intent, module list, module boundaries (charter "模块边界", B-n), project acceptance criteria, decisions | Module internals, task details, code |
  | Module (module agent) | Its own spec, interfaces, tasks, code | Internals of other modules (public interfaces only) |
  | Task (developer) | A self-contained contract (interface excerpts and verbatim requirements included) and its own owns | Other tasks |

  Cross-module information is obtained in order: ① read the other module's `interfaces.md` and the charter "模块边界" (Module boundaries); ② not enough → send a QUESTION to the owning module, facts only; the answer gives a file pointer and the asker records it in the "依赖" (Dependencies) section of its own spec; ③ the other module is done → read its `acceptance.md` and the code on its module branch, then ask the pm if still unclear; ④ interface changes only go through the pm (ESCALATE → DECISION + ADR).
- **Baseline module**: the first module in the list is always `baseline` (`kind: baseline`). It goes through the normal W2 + W3; its contract is what the former Environment baseline (「环境基线」) step required (environment.md, AGENTS.md, smoke tests, check scripts, shared skeleton, explicit switches, constraint enforcement, integration-test tool). The environment and skeleton are therefore reviewed and accepted too. Every other module depends on it and branches off `mod/baseline` (or the branch of the functional module it depends on).
- **Integration-test module** (when `integration_test` is not off): the last module in the list, `integration-test`, depends on all other modules. It starts automatically once they are done, merges every module branch into the integration branch, and writes and runs automated integration tests against the assembled product; the defects it finds go through the pm to fix-module tasks of the owning modules. See sections 4–6.
- **Long-running sessions only route**: W1 Coordination (「调度」) and W2 Waiting on development (「等待开发」) treat NOW and the files as authoritative whether or not the conversation history is still there, and hand events on; investigation, acceptance and coding happen in one-off sessions whose results are written to files.
- **Merge conflicts are fix items too**: conflicts that only touch environment.md "共享文件" (Shared files) are resolved in place (keep both sides' appended entries, regenerate generated files with their command). For other files, the integration-test module, multi-dependency Module planning, re-merges and Project acceptance never resolve them: `merge --abort`, write a fix item (conflicting files, the two modules, owner = the module merged later), and the pm creates a fix-module task (owns = the owning module's source paths from the charter module list + the conflicting files; it merges the owning module's branch and resolves the conflict).
- **One current branch per module**: `current_branch` in registry.json records the original branch or the latest fix branch; every place that "merges the module branches" merges only current branches, so the same conflict does not reappear by merging an old branch and then its fix branch. When a fix module finishes, the pm updates `current_branch` and sends a NOTICE to modules that depend on it and are still in progress; they merge the fix branch into their own module branch in Waiting on development.
- **Fix modules stay light**: scope `mod:<module>-fix-<n>`, with its own `modules/<module>-fix-<n>/`; the original module directory is read-only; usually one task; acceptance only re-runs the fix item's failing tests and the merge gate. If it believes a defect was misrouted (not its module, or the test itself is wrong), it reports misrouted with evidence and moves itself to Done; the pm marks it dropped in status.json. If the source was an integration-test defect, it goes back to the integration-test module and the reporting test task re-judges it (that round does not count toward the fix-round limit); if the source was a Project acceptance fix item, it is recorded in status.json for the next Project acceptance to judge.
- **Known issues**: when the pm accepts an integration-test defect as a known issue (DECISION + ADR), the integration-test module moves the test task back to Develop to mark the failing case as an expected failure citing the ADR, then report normally; review does not count that as weakening a test, and both module and project acceptance record unverified(known issue, ADR), listed under things the user needs to handle, not fail.
- **Fix items and routing notes**: verifiers (review, module acceptance, project acceptance) write each failure as a fix item that can be dispatched as is (number, owning module or task, reproduction steps, expected, actual, suspected location, the failing test or acceptance item); a KMSG unrelated to the current step is not handled but recorded verbatim in the round's "转交" (Handover) section. When long-running sessions and the pm dispatch fixes, the contract = a pointer to the original fix item or defect (file + number) + a note of at most two sentences; nothing is rewritten or added.

### Roles and profiles

| Role (key in profiles.json) | Used in | Suggested model | Session |
|---|---|---|---|
| `intake` (optional, defaults to mechanical) | W1 Intake (接收) | A light model is enough (e.g. Sonnet): it only fills in parameters and asks questions, no planning | New session every time, closed on completion |
| `pm` | W1 Project planning (立项规划) / Module dispatch (模块下发) / Coordination (调度) / Refresh (刷新) | Strong model | Long-lived; Coordination resets context on entry |
| `plan_auditor` (optional, defaults to auditor) | W1 Plan review (立项评审) | Small context, biggest impact: the strongest model fits; the profile must differ from pm | New session every time |
| `auditor` | W1 Project acceptance (项目验收) | Strong model; the profile must differ from pm | New session every time |
| `module` (optional, defaults to pm) | W2 Module planning (模块规划) / Waiting on development (等待开发) / Refresh (刷新) | Strong model | One session per module; Waiting on development resets context on entry |
| `module_auditor` (optional, defaults to auditor) | W2 Acceptance check (验收调查) | Strong model; the profile must differ from module | New session every time |
| `developer` | W3 Develop (开发) | Main coding model | One session per task, reused when sent back |
| `reviewer` | W3 Review (审核) | The profile must differ from developer, ideally from a different vendor | New session every time |
| `mechanical` | W3 Merge (合并, merge gate), W1 Final merge (收尾合并) | A coding model (it must read failure output and resolve conflicts within its own scope) | New session every time; short mechanical header, NOW is read-only and not executed |
| guard | Kandev automation; decisions are made by `kandev/stage.py` | Cheap model | One new session per run |

## 3. Run modes

The `[TASK v1]` header in the pm task description sets `mode: attended | unattended`; module tasks and development tasks inherit the same value.

| | attended (default) | unattended |
|---|---|---|
| Plan approval (立项确认) | After plan review passes, wait for the user to approve | After plan review passes, go straight to Module dispatch |
| Asking the user | Allowed, batched into a single question round (each question with a recommended answer) | No questions. Decide on its own, write an ADR, and log it in `project/attention.md` |
| The environment needs user configuration (e.g. Copy files) | The baseline module escalates to the pm, who asks the user | Pick an approach that does not depend on user configuration; the pm writes an ADR |
| Final human review (人工终审) | The user | The user (handled when they come back) |

**plan_only** (`plan_only: true` in the `[TASK v1]` header): regardless of mode, the task stops at Plan approval (「立项确认」) after plan review passes. The user first checks the charter and the requirement coverage table, and once satisfied drags the task to Module dispatch (「模块下发」) to continue, before committing development quota.

**integration_test** (`integration_test: auto | off` in the `[TASK v1]` header, default auto): with auto, the pm adds the integration-test module to the charter and integration testing starts automatically once all other modules are done; with off it is not added, and module branches are merged for the first time in Project acceptance.

The user only needs to watch two places: `project/attention.md` (things the user needs to decide, each with a recommended answer and a default action) and `agents/guard/stage.md` (who the system is waiting on right now, generated by the guard script).

## 4. W1 Project management

| # | Step | Role | What it does | Transition |
|---|---|---|---|---|
| 0 | **Intake (接收)** | intake | Entry point. A description that already is a complete `[TASK v1]` header passes through unchanged; otherwise, following [intake.md](intake.md) (Chinese), derive what can be derived (repository, baseline branch, project name, management directory, template path), ask the user for the rest (at most 4 questions per batch, at most 3 batches), and rewrite the task description as a `[TASK v1]` header + the user's original text; no planning, no repository changes | Completion signal → Project planning |
| 1 | Project planning (立项规划) | pm | Initialize the management directory; write the charter (verbatim requirements R-n, module list with baseline first and the integration-test module last, module boundaries B-n, PAs and their covers), conventions, ADRs, attention; no code | Completion signal → Plan review |
| 2 | Plan review (立项评审) | plan_auditor | Independently review the charter: requirement coverage table (one row per R) + one verdict line for each of checks 1–6 (including module size, boundary coverage and the baseline module), written to the task doc `charter-review` | Send back → Project planning (≤2 times); still blocking on the 3rd review → recorded in charter-review, Plan approval (regardless of mode); pass: plan_only or attended → Plan approval, unattended → Module dispatch |
| 3 | Plan approval (立项确认) | human (session bound to pm) | Gate (attended or plan_only) | Drag to Module dispatch = approve; send a message in the pm session = back to Project planning with comments |
| 4 | Module dispatch (模块下发) | pm | Driven by state, not by entry count: first create the modules not yet created (create the `mod/baseline` branch; baseline first, its contract is fixed text in the script; the others blocked_by baseline, branching off `mod/baseline` or the module they depend on; the integration-test module last); then dispatch items to fix and final-review comments as fix-module tasks by pointer; only when neither exists is there nothing to do | Completion signal → Coordination |
| 5 | Coordination (调度) | pm | Long-running, routing only (context reset on entry): reports, escalations, questions, alerts; integration-test defects or merge conflicts → fix-module task for the owning module, then tell the integration-test module to re-run; decisions affecting a finished module also become fix-module tasks | Once all modules are done, the agent moves itself to Project acceptance |
| 6 | Project acceptance (项目验收) | auditor | Create or update the integration branch (cut from the baseline branch), merge all module branches, run the full tests and the integration tests, verify the PAs, check each R one by one; write the final-report (including quota usage, how to run the final review, things the user needs to handle, temporary resources); failures and merge conflicts written as fix items | No fail, or still failing on the 3rd entry (listed under things the user needs to handle) → Final human review; any fail → Module dispatch |
| 7 | Final human review (人工终审) | human (session bound to pm) | Gate | **Drag to Final merge = approve**; send a message in the pm session = back to Module dispatch with comments |
| 8 | Final merge (收尾合并) | mechanical | Merge the integration branch into the baseline branch, run smoke tests, clean up temporary resources, restore the recorded push URLs, set status to done | Completion signal → Done |
| 9 | Done (完成) | — | Task complete | — |
| 10 | Refresh (刷新) | pm | After resetting context, move back to the original step (`刷新返回：` in the move instructions first, then NOW) | The agent moves itself |

## 5. W2 Module management

| # | Step | Role | What it does | Transition |
|---|---|---|---|---|
| 0 | **Module planning (模块规划)** | module | Write spec (MAs and their covers, covering the contract's acceptance points and related B-n) / interfaces (implementing the B-n this module provides) / tasks.json (each task with `tests` and `boundaries`); run `tools/check_tasks.py`; create development subtasks with self-contained contracts: those without prerequisites go to Develop (「开发」), those with prerequisites go to Queued (「待开发」) | Completion signal → Waiting on development |
| 1 | Waiting on development (等待开发) | module | Long-running, routing only: answer subtask questions; handle tasks in Awaiting decision (「等待决策」) and merge-gate escalations (move back to Develop with instructions, move to Done, or split); update tasks.json when a REPORT arrives and release Queued tasks whose prerequisites are merged; create fix subtasks from the auditor's fix items | All subtasks in a terminal state (on_children_completed) → Acceptance check. The module agent moves there itself only in two cases: it entered with an acceptance send-back and no subtask is left non-terminal, or after handling a pm DECISION all are terminal with none held |
| 2 | Acceptance check (验收调查) | module_auditor | Independent module auditor (new session): check subtask status first (tasks marked failed / dropped in tasks.json are not a problem); coverage check; run module tests and judge each MA (known issues accepted by the pm are unverified); write this round in acceptance.md with fix items. Fix modules check only the fix items | Pass → REPORT to the pm, Done; any fail → Waiting on development (round 3, or other modules involved: ESCALATE to the pm first) |
| 3 | Done (完成) | — | | |
| 4 | Refresh (刷新) | module | After resetting context, move back to the original step (instructions first, then NOW); if all subtasks are already in a terminal state, go straight to Acceptance check | The agent moves itself |

The auditor does not write tasks.json (single writer): on a send-back the module agent writes `passes` back from acceptance.md; once acceptance passes the module ends, and the last round of acceptance.md is authoritative.

**Baseline module** (task header has `kind: baseline`): the module agent writes `project/environment.md` (commands and results taken from the subtasks' reports) and performs the non-code enforcement actions (`git remote set-url --push`, initializing the quota ledger); files in the repository are written by development subtasks and go through review and the merge gate. When user configuration (Copy files) is needed it escalates to the pm. The auditor runs the smoke tests and check scripts in a fresh worktree.

The **integration-test module** (task header has `kind: integration`) goes through the same steps with different content:

| Step | What differs |
|---|---|
| Module planning | First creates or updates the integration branch in its own task worktree, merging the branches of all other modules (conflicts become fix items for the pm), then cuts `mod/integration-test` from it (so it gets the latest code of every module). MAs are cross-module user scenarios; subtasks are integration-test tasks (`kind: integration-test`, owns inside the integration-test directory) |
| Waiting on development | When an integration-test task reports defects (each naming its owning module; the task waits in Awaiting decision), it neither fixes nor confirms them itself: it ESCALATEs to the pm. When the pm reports the fix is done, it merges the fix branch into the integration branch and `mod/integration-test` and moves the task back to Develop to re-run; when the pm forwards a misrouted report, it moves the task back the same way so the test task re-judges |
| Acceptance check | Runs the full tests and the integration-test command, checking each scenario |

## 6. W3 Development

| # | Step | Role | What it does | Transition |
|---|---|---|---|---|
| 0 | Queued (待开发) | — | Parks subtasks that have prerequisites (does not count toward WIP, does not start a session) | Once prerequisites are merged, the module agent moves it to Develop |
| 1 | **Develop (开发)** (WIP 4) | developer | Smoke test (skipped when none exists yet) → implement the self-contained contract (`shared` files: append own entries only) → tests + owns check → write report → commit; no change needed → suggest dropped; cannot finish → blocked | Completion signal → Review; dropped / blocked / defects → ESCALATE to the module agent (message_task) and move itself to Awaiting decision; ordinary questions stay in Develop |
| 2 | Review (审核) | reviewer | Re-run the tests and owns check exactly as given; for each AC write the evidence it personally confirmed (write unverified for what it cannot confirm), spot-check at least 1 edge case; write review | pass → Merge; minor → Develop (≤3 rounds, counted since the module agent's last INSTRUCT / contract change); direction → Awaiting decision and ESCALATE |
| 3 | Awaiting decision (等待决策) | — | No WIP; review direction issues and the developer's blocked / dropped / defect reports wait here for the module agent | The module agent moves it back to Develop with instructions, or to Done |
| 4 | Merge (合并) | mechanical | Merge gate: first check whether it is already merged; rebase onto the latest module branch; run environment.md "合并门禁" (Merge gate) commands and the owns check; on pass, fast-forward the module branch itself (no PR) and send a REPORT to the module agent | Merged → Done; gate failed → Develop (3rd time: ESCALATE to the module agent) |
| 5 | Done (完成) | — | | |

**Integration-test tasks** (contract marked `kind: integration-test`): the developer writes automated tests against the really assembled application, using the tool in environment.md "结合测试" (Integration tests), and asserts user-visible results and data state; only scenarios the tool cannot cover are checked by operating the product manually, with the reason and evidence recorded. When a test fails because of a product defect, the failing case is kept, the report says `result=blocked` with `defects` (each naming the owning module and the suspected location), and the module agent is notified — assertions are not changed, no mocks are added, nothing is skipped. The reviewer checks that the tests run against the real application and that nothing was mocked, skipped or loosened to make them pass.

For the specific requirements on development and review regarding tests, screenshots and so on, see the [project conventions](project-conventions.en.md).

## 7. Context and continuity

- **Prevention**: work is split along knowledge boundaries, and each agent reads only the files its level needs; one session per task; information is passed across steps through handoffs, task docs and the management directory; resident context is kept very small (AGENTS.md ≤150 lines, stable prompts with no timestamps, which helps cache hits).
- **Long-running steps go by the files**: the on_enter of Coordination (「调度」) and Waiting on development (「等待开发」) includes reset_agent_context, but returning from Acceptance check involves a profile switch and the platform may skip the reset, so the prompt says "whether or not the conversation history is still there, NOW and the files are authoritative".
- **Refresh**: when the session of a long-running step gets too long, the agent first writes `刷新返回：<step>` into NOW, then moves to the Refresh (「刷新」) step; when the guard moves an unresponsive pm to Refresh, it puts `刷新返回：<original step>` in the move instructions (Refresh reads that first). The Refresh step resets context on entry, then moves back to the original step. Kandev does not allow moving a task to its current step, so it has to go through this relay step.
- **Guard**: one Kandev automation per workspace, running every 15–20 minutes; it discovers all in-progress projects on its own, patrols read-only, and sends ALERTs to the upstream manager. `kandev/stage.py` decides who each task is "waiting on" using a fixed rule table (the first matching rule wins); the guard only executes the alerts the script produces, and generates `agents/guard/stage.md` for the user. The rules are in "阶段分类" (Stage classification) of `mgmt-template/roles/guard.md` (Chinese).
- **On recovery, check external state first**: before re-creating tasks, merging, pushing, making real calls or deleting resources, check the actual state; anything that has already taken effect is not redone. The Refresh step first checks "未确认的意图" (unconfirmed intents) in NOW.

## 8. Concurrency and WIP

- The WIP of the Develop step is a global cap shared by all modules (default 4), used to limit how many agents run on the machine at once.
- Kandev counts WIP as "tasks in this step", so tasks blocked by blocked_by also take up slots, and the dependency chain drags parallel work into serial work. That is why W3 has a Queued (「待开发」) step that does not count toward WIP: tasks with prerequisites are created there with `start_agent=false` and **no Kandev blocked_by**; prerequisites are recorded only in tasks.json (the guard reads them from there too). Once every prerequisite is merged in tasks.json (REPORT received, commit confirmed on `mod/<module>` with `git merge-base --is-ancestor`) or dropped, the module agent moves the task to Develop. blocked_by between modules (W2 tasks) stays as it is.
- Dependency chains are still best kept shallow; work that must be serial is merged into a single task.
- Every module is blocked_by baseline; between the other modules, use blocked_by where they depend on each other (and branch off the module depended on), and none where they can run in parallel on the skeleton.
- Development tasks waiting on the module agent's decision (blocked / dropped / defect reports) move to Awaiting decision (「等待决策」), which does not count toward WIP.

## 9. Branches and merging

```
baseline branch ← Final merge ← integration ← Project acceptance ← mod/<module> ← merge gate (fast-forward) ← development worktree branch
                                                                     ↑ cut from mod/baseline (mod/baseline is cut from the baseline branch)
```

- Module dispatch creates `mod/baseline` from the baseline branch; modules with no functional dependency are cut from `mod/baseline`, and modules depending on another functional module are cut from that module's branch (with several dependencies, base is one of them and the rest are merged in at step 1 of Module planning), so that e.g. a UI module develops against the real backend code.
- Merge conflicts (Module planning, the integration-test module, Project acceptance) are never resolved by the merger; they become fix items for the pm, see section 2. The user's baseline branch is not touched before Final merge (「收尾合并」).
- When creating W2 tasks, `base_branch` is always `mod/baseline` (the baseline module itself uses the baseline branch); it only decides the module agent's own worktree. A module branch's real starting point is written only on the branch line of the [TASK v1] header and created with git at step 1 of Module planning.
- Development subtasks are cut from the module branch via `base_branch=mod/<module>`. The Merge step rebases onto the latest module branch and, after passing the merge gate, fast-forwards the module branch itself (`git fetch . HEAD:mod/<module>`, fast-forward only; a failure means another task merged first, so rebase again). `mod/*` exists only locally and the baseline disables pushing by default, so PRs are not supported at this level.
- The integration-test module creates the integration branch (cut from the baseline branch) during planning and merges the current branches (`current_branch`) of all other modules into it (including `mod/baseline`); `mod/integration-test` is cut from integration.
- Fix-module tasks (`mod/<module>-fix-<n>`) are cut from the integration branch, or from the owning module's current branch when the integration branch does not exist yet (interface changes during development, multi-dependency merge conflicts, `integration_test: off`). Once fixed, the fix branch becomes that module's `current_branch` and is merged into the integration branch by the integration-test module (or by Project acceptance).
- Project acceptance updates the integration branch and merges each module's current branch from the registry; without an integration-test module, Project acceptance creates it.
- After the user approves in Final human review, Final merge merges integration into the baseline branch and restores each remote's push URL from the record in environment.md "约束落实" (the baseline module records the original URL when it disables pushing; the repository goes back to the user when the project ends).
- Whether Final merge merges locally or via PR (for a PR, restore the push URL first), the merge-gate commands and whether to push to the remote are defined by each project's environment.md; see the [project conventions](project-conventions.en.md).

## 10. Boundary with the project being developed

The architecture only defines **who, at which step, and how** project conventions are handled; the actual content (quota, side effects, constraint list, test commands, screenshots, merging and pushing) belongs to each project being developed; see the [project conventions](project-conventions.en.md).

| Defined by the architecture | Where |
|---|---|
| Project planning writes the conventions into the project's conventions; the baseline module implements the enforceable constraints as code | W1 Project planning; baseline module (W2 + W3) |
| Run the check scripts before Develop reports and during Review; run the merge gate before merging; re-run tests exactly as written in environment.md; environment.md "共享文件" (Shared files) lists files several tasks append entries to (tasks.json `shared`) | W3 Develop, Review, Merge |
| When blocked by a constraint enforced in code, stop and report — do not work around it; constraints that cannot be enforced are labeled "prompt only" | 【通用规则】 (general rules) in every prompt |
| Project acceptance reports quota usage | W1 Project acceptance |


## 11. Deployment and launch

For deployment steps see [kandev/README.en.md](../kandev/README.en.md); to have an agent deploy and verify for you, see [AGENTS.md](../AGENTS.md) (Chinese).

To launch a project: create a task in 「多Agent · 项目管理」 (W1 Project management), select the repository and baseline branch, write the requirements in the description, then choose Start task.

The description may contain only the requirements (mention any parameter you care about in a sentence, e.g. "run unattended", "plan only first"). The task starts in Intake (「接收」): it derives the repository path, baseline branch, project name, management directory and template path, asks you for the remaining parameters (run mode, whether to stop after planning, whether to run integration tests, ...), then rewrites the description into the format below for the pm. Fields, defaults and questions are in [intake.md](intake.md) (Chinese).

If the description is already complete in the format below (for example a task created by an agent following section C of [AGENTS.md](../AGENTS.md)), Intake changes nothing, asks nothing, and goes straight to Project planning.

```
[TASK v1]
project: <project name>
mode: attended | unattended
plan_only: false            # true: stop at 「立项确认」 (Plan approval) after plan review passes
integration_test: auto      # auto: run integration tests automatically once the other modules are done; off: skip
mgmt_root: <absolute path of the management directory, outside the repository and worktrees>
mgmt_template: <absolute path of this repository's mgmt-template>
repo: <absolute path of the main repository>
role: pm
scope: pm
parent: user
pm: self
branch: <auto> base <baseline branch>
---
<project goal, requirements (sorted by importance, one per line; the pm will excerpt each as R-n), constraints, tech stack and environment requirements (handed to the baseline module), quota agreement (see the project conventions)>
```

Header of a module task created by the pm (baseline / regular module):

```
[TASK v1]
role: module
scope: mod:baseline            # regular module: mod:<module>
kind: baseline                 # omitted for regular modules; integration-test module: integration
mode: <same as pm>
mgmt_root: <same as pm>
parent: pm @ task <pm task id>
pm: task <pm task id>
branch: mod/baseline base <baseline branch>   # regular module: mod/<module> base mod/baseline (base mod/<dependency> when it depends on another functional module)
---
<module contract>
```

## 12. Known limitations

- The external MCP has no `message_task_kandev` and cannot create automations. An external guard or observer can only move tasks and answer questions and permission requests on an agent's behalf. Work that needs these capabilities is written as a handoff prompt (`kandev/handoff/`) and given to an agent inside Kandev to execute.
- `on_children_completed` only fires while the task is in Waiting on development (「等待开发」). The Refresh step checks subtask status to close this gap.
- Kandev records context usage within a session, but MCP cannot read it, so the guard can only look at indirect signals.
- Exported workflow files record profiles only by model / mode. With several profiles on the same model they may be matched incorrectly, so deployment uses `build_workflows.py`, which binds by ID.
- A user message in a gate is delivered to the session tab the user is in, not to the next step's session, and a move triggered by a user message does not reliably deliver the next step's prompt. So: gate steps are bound to the pm profile (entering the gate closes the reviewer session and makes the pm session current); when the pm receives a direct user message it works out which step it is in and handles it (【用户直接消息】); if a reviewer session receives one anyway, it forwards it to the pm session (`kandev_session_id` in the registry); and on re-entering Project planning or Module dispatch the pm collects comments from several sources. If the pm still does not start, move the task to the gate and back to that step, with the comments verbatim in the move instructions.
- Queued (「待开发」) relies on two Kandev behaviors that must be verified after deployment (see "B. 验收部署" (Verify the deployment) in [AGENTS.md](../AGENTS.md)): when `create_task_kandev` is called with `workflow_step_id` and `start_agent=false`, the task stays in that step without starting a session; moving from a step with no agent to Develop (「开发」) triggers the on_enter auto_start.
- The Merge step sends its REPORT before calling step_complete_kandev, so the release condition is "the prerequisite's REPORT has arrived and its commit is on the module branch", not the Kandev state; Queued tasks have no blocked_by, so the move is not affected by the platform's dependency checks.
- When Waiting on development and Acceptance check alternate, the module agent's session (profile `module`) and the auditor's session (profile `module_auditor`) take turns within the same Kandev task; Waiting on development goes by NOW and the files and does not rely on the earlier conversation.

### Platform behaviors to verify after deployment

The design relies on the following behaviors, which have not yet been tested on a local Kandev; each comes with a fallback if it does not hold.

- a. Moving a task from Queued (「待开发」) to Develop (「开发」) triggers auto-start (on_enter auto_start). Verified on 2026-11-13 with both Codex and Claude agents. Fallback: tasks with prerequisites are created by the module agent directly in Develop once the prerequisites are merged.
- b. When an agent moves itself to Awaiting decision (「等待决策」), its development session is kept and reused when moved back. Verified on 2026-11-13 (same runs). Fallback: the move-back instructions say to read the task docs now and report first (already written).
- c. on_children_completed fires again after a new batch of fix subtasks all completes. Fallback: relax the condition for the module moving itself to Acceptance check to "all subtasks terminal".
- d. In a task with several sessions, a message without session_id goes to the current step's session, and multiple moves on the same task run in the order sent. Fallback: send messages with the session_id recorded in the registry; the guard's alerts are the safety net.
- e. All worktrees share the local `mod/*` branches. Fallback: push to a local bare remote instead.
- f. Continuing after a usage limit, and moving out and back after a session failure, actually recover; the instructions attached when the guard moves a task are delivered. Fallback: `agents/guard/stage.md` shows these states, and the user acts manually.
- g. The Intake agent can rewrite its own task's description with `update_task_kandev`, and `{{task_prompt}}` in Project planning then resolves to the new description. Fallback: Intake also writes the new description to the task doc `intake`; when the description has no `[TASK v1]` header the pm re-reads the task, then that section; if the rewrite fails, Intake prints the full text and the user pastes it into the task description and drags the task to Project planning.

## 13. Rejected designs

Approaches that were tried or evaluated and then abandoned, with the reasons, so we don't walk back into them later.

| Approach | Why rejected | What we do now |
|---|---|---|
| Refresh a long-running step by "moving to the current step + reset_context" | Kandev's entry_options require an actual step change; moving to the current step is a no-op | The Refresh (「刷新」) relay step |
| Let an external scheduled guard pass the gates | Polling interval is 20 minutes, so a gate waits about 10 minutes on average | Plan review passes the gate inside the workflow |
| Rely only on test-config defaults to block quota-consuming calls | A single command-line argument can override them; real calls exceeded the quota in an actual run | Explicit switch + code check + quota ledger |
| `git add -A` in the management directory | Commits files owned by others along with your own | Only add your own paths + pre-commit hook |
| Set session_target on Plan approval | Suspected of creating an extra empty session | Not set; gate steps are bound to the pm profile instead |
| Gate steps without a profile, relying on on_turn_start to carry the message back to the pm's step | The gate inherited the reviewer's session; the user replied there, the message stayed with the reviewer, and the pm session woke up without receiving a prompt (observed) | Gates bound to pm + pm collects comments from several sources + reviewer forwards |
| Many restrictive clauses in prompts (only do what the contract says, no opportunistic improvements, no implementation approach, no style comments, check only the literal conditions, fixed module count and dependency depth) | Everything passed literally but the user found the result bare, and features that passed under mocks failed in real use (observed); the restrictions suppressed the model's own judgment | Principle 12: keep only boundaries and completion conditions, leave the approach to the agent; one short 【主动性】 (initiative) rule |
| Put tasks with prerequisites directly in Develop and wait with blocked_by | Blocked tasks also take WIP, so the dependency chain drags parallel work into serial work | Park in Queued (「待开发」), which does not count toward WIP, and let the module agent release them |
| Also set Kandev blocked_by on Queued tasks | The platform does not check dependencies when moving, so a move may succeed without starting a session; release would also wait for the prerequisite to reach Done in Kandev, later than its REPORT | Prerequisites only in tasks.json; release on REPORT + `merge-base --is-ancestor` |
| Merge development branches into the module branch through PRs | `mod/*` exists only locally and the baseline disables pushing by default, so PRs cannot work; a PR merge does not wake the module agent either | The Merge step fast-forwards locally after the gate; PR is optional only in Final merge |
| Use Kandev's pull_from_step to pull tasks from Queued into Develop | Unclear whether blocked_by is checked when pulling; the release condition (prerequisites merged) is clearer when decided by the module agent | The module agent moves them |
| Move Develop to a WIP-free "等待回答" (Awaiting answer) step while waiting for the module's answer | The answer starts a new turn via message_task, and its behavior in a step with no agent has not been verified | Not adopted for now |
| The user hand-writes the complete `[TASK v1]` header to launch a project | Most of the dozen parameters can be derived or have defaults; hand-writing is error-prone and a high barrier | The Intake step (「接收」): a light model derives, asks, and rewrites the description; a complete header passes through unchanged |
| Have the guard use an LLM to read signals and decide | Not reproducible, hard to test | `stage.py` rule table + regression tests |
| Create a separate guard automation for each project | Requires manual configuration every time a project starts, and cleanup when it ends | One guard per workspace, which discovers projects on its own from the pm task's `[TASK v1]` header |
| Infer "is it waiting on a human" from conversation text or free-text reports | Needs structured facts | Use only Kandev state, pending questions and permission requests |
| Merge module branches for the first time in Project acceptance, which only runs existing tests | No task was responsible for writing cross-module tests, and the auditor cannot write code; every module passed, yet an item deleted in the UI was still shown and could not be deleted (observed) | Integration-test module: after the other modules are done, merge and write automated integration tests |
| Have the pm dispatch the integration-test task from Coordination after all modules are done | Re-entry of Module dispatch is already used for items to fix and final-review comments; it would need another entry reason and another W1 loop | Create it at first dispatch, blocked_by all other modules; its branch is only created when it starts, so it still gets the latest code |
| The pm builds the environment baseline itself (the W1 「环境基线」 step) | The pm has to write code, the skeleton and scripts get no review or acceptance, and the pm's context fills up with environment details | The baseline module goes through W2 + W3, with review, the merge gate and module acceptance |
| The module agent accepts its own module | The planner verifying its own plan tends to check only the MAs it wrote, missing contract points and module boundaries; the long-running context also keeps growing | Acceptance check (「验收调查」) is done by an independent module auditor (module_auditor, new session), starting with a coverage check |
| The module agent merges subtask branches one by one | The long-running session has to read diffs, run tests and handle conflicts; its context swells and it becomes a serial bottleneck | The Merge step runs the merge gate and fast-forwards itself; the module agent only updates tasks.json |
| Small-project variant: drop W2 and let the pm create development subtasks directly | The prompts have no such path, and the pm does not hold module-internal knowledge; maintaining a separate flow for it is not worth it | Small projects also go through W2; a module may have just one or two tasks |
| The integration-test module fixes defects itself | It does not hold other modules' knowledge, so fixing means reading other modules' internals, breaking the knowledge boundary | Defects name the owning module and go through the pm to that module's fix-module task |
