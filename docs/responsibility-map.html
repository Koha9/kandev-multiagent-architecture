Agent 责任分工图

三套 workflow 的每个步骤由谁负责、会话怎么开，以及每条打回 / 升级路径的落点（落点即承担返工的角色）。

方案 A 相对现状的变化（图中黄色描边 / 「改」角标 / ★ 标签为变化处）
  1. W2「验收调查」改由 auditor 负责，每次新会话；只判定并写验收记录，有问题带意见退回「等待开发」（⑩），由模块 agent（pm）建修复任务。
  2. 结合测试测出的缺陷改为上报 W1 调度（㉒）→ pm 为担当模块建修复模块任务（㉓，一轮 W2 + W3）→ 修复合入后结合测试模块重新合并并重跑（㉔）；上限 2 轮，仍不通过交给用户（㉕）。取消 ⑲ ⑳ ㉑ 和结合测试模块内的修复子任务。
  3. 立项评审新增检查：模块过大或职责过多时退回立项规划拆分（②）。
方案 B 的两条规则
  1. 一个 agent 只持有一层知识：项目层（pm）、模块层（模块 agent）、任务层（开发）。
  2. 常驻会话只做路由，重活放进用完即弃的新会话；验证者的结论写成「可直接下发的修复项」（复现步骤、期望、实际、疑似位置、担当模块、失败的测试）。
相对现状的变化（图中黄色描边 / 「改」角标 / ★ 标签为变化处）
  1. W1 去掉「环境基线」（共 11 步，后续步骤顺次编号）。原基线工作（骨架、冒烟测试、检查脚本、结合测试工具）由新增的 baseline 模块经 W2 + W3 完成，因此有审核和验收；它最先执行，其他模块都依赖它（W3 泳道左侧黄色虚线框）。④ ⑤ 不再存在。
  2. W1「调度」与 W2「等待开发」仍常驻，但进入时重置上下文，只做路由。
  3. W2「验收调查」改由 auditor 新会话负责：写好修复项，模块 agent 只建修复子任务（⑩ 轻）；第 3 次仍不过或涉及其他模块，由 auditor 直接升级给调度（⑪）。
  4. 项目验收有 fail 时 auditor 已写好修复项和担当模块，pm 只建修复模块任务（⑥ 轻）。立项评审的阻塞问题与模块过大共用 ≤2 次（①）。
  5. 结合测试：结合测试模块 agent 先确认是产品缺陷并写明担当模块（⑲），再上报调度（㉖ 轻）→ pm 建修复模块任务（㉓）→ 重新合并并重跑（㉔），≤2 轮后交用户（㉕）。
  6. W3 开发契约自包含（模块 agent 摘入相关接口片段和需求原话）；新增跨模块查询（靛蓝点划线，不计入返工）。
  7. 守护把无响应的 pm 移到「刷新」这条保留：进入时重置只清掉进入之前的历史，常驻步骤长时间停留仍会累积上下文，会话卡死也要靠它恢复。
  8. 缺口：结合测试缺陷的确认与归属由结合测试模块 agent（常驻「等待开发」实例）自己做，与规则 2 冲突——见方案 C。
方案 C = 方案 B + 下面 6 项。方案 C 不新增角色和步骤，只把机械性的工作从常驻会话移给脚本和一次性会话。
  1. C1 缺陷归属由发现它的测试任务完成（修正 B 的缺口）：结合测试任务（developer，一次性会话）在 defects 里直接写明担当模块和疑似位置，审核核对；结合测试模块 agent 只转交（⑲ 改为轻）。
  2. C2 路由备注规则（借鉴 dsh-superagent：主会话只转发原始内容加不超过 30 词的备注，不添加要求）：常驻会话下发修复时只给指向原修复项的指针和一句备注，不改写（㉓ 改为轻；⑥ ⑩ 在 B 中已是轻）。
  3. C3 合并门禁（借鉴 Anthropic C 编译器项目和 OpenAI harness：共享分支上的无回归门禁，机械强制优于文字规则）：「合并」在 rebase 后运行完整本地检查脚本（lint + 全量测试 + 构建，有结合测试套件时一并运行）。失败直接退回「开发」（㉘，developer 原会话，≤2 次），超过再升级模块 agent（㉙）。取代 ㉗。
  4. C4 合并下沉（借鉴 Cursor：去掉 integrator 角色，worker 自己处理合并）：门禁通过后「合并」步骤自己合入模块分支并移到完成；模块 agent 不再合并，只在收到 REPORT 时放行后续任务。
  5. C5 契约检查脚本（借鉴 MAST：约 44% 的失败来自规格和系统设计；OpenAI：机械强制）：模块 agent 创建子任务前运行确定性脚本，检查 owns 不重叠、每个任务有 AC 和测试命令、每条跨模块边界都落到某个任务、依赖无环。不是新的评审步骤。
  6. C7 验收标准的覆盖核对（借鉴 Anthropic 长任务 harness：验收标准要明确、不可随意改动；MAST：验证只做表面检查是常见失败）：auditor 做模块验收时，先核对模块 agent 写的 MA 是否覆盖了 pm 模块契约里的每条验收要点和 charter「模块边界」中与本模块有关的每一行（做法同立项评审的需求覆盖表），有缺口即判不通过。原因：MA 是被验收方自己写的，且开工前没有独立评审。不新增路径，不改变落点数字。
  7. C6 其余保留 B：知识分层、常驻步骤进入时重置、验收调查由 auditor 做、baseline 模块、跨模块查询；守护移到「刷新」同样保留。
