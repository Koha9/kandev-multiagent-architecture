三套 workflow 的每个步骤由谁负责、会话怎么开，以及每条打回 / 升级路径的落点（落点即承担返工的角色）。v3.2 视图取自 v3.2 三轮纸面模拟后的 docs/workflow.md、docs/prompts.md 和 mgmt-template/roles/guard.md，尚未在真实项目中运行。

相对于

v3.1 是已部署的版本：W1 有「环境基线」（pm 自己做），W2 全部用 pm profile，验收调查由模块 agent 在同一 profile 下重置上下文后做；结合测试缺陷由结合测试模块自己建修复子任务。

方案 A 相对 v3.1 的变化
  1. W2「验收调查」改由 auditor 负责，每次新会话；只判定并写验收记录，有问题带意见退回「等待开发」（⑩），由模块 agent（pm）建修复任务。
  2. 结合测试测出的缺陷改为上报 W1 调度（㉒）→ pm 为担当模块建修复模块任务（㉓，一轮 W2 + W3）→ 修复合入后结合测试模块重新合并并重跑（㉔）；上限 2 轮，仍不通过交给用户（㉕）。取消 ⑲ ⑳ ㉑ 和结合测试模块内的修复子任务。
  3. 立项评审新增检查：模块过大或职责过多时退回立项规划拆分（②）。
方案 B 的两条规则
  1. 一个 agent 只持有一层知识：项目层（pm）、模块层（模块 agent）、任务层（开发）。
  2. 常驻会话只做路由，重活放进用完即弃的新会话；验证者的结论写成「可直接下发的修复项」（复现步骤、期望、实际、疑似位置、担当模块、失败的测试）。
相对 v3.1 的变化
  1. W1 去掉「环境基线」（共 11 步，后续步骤顺次编号）。原基线工作由新增的 baseline 模块经 W2 + W3 完成，因此有审核和验收；它最先执行，其他模块都依赖它（W3 泳道左侧虚线框）。④ ⑤ 不再存在。
  2. W1「调度」与 W2「等待开发」仍常驻，但进入时重置上下文，只做路由。
  3. W2「验收调查」改由 auditor 新会话负责：写好修复项，模块 agent 只建修复子任务（⑩ 轻）；第 3 次仍不过或涉及其他模块，由 auditor 直接升级给调度（⑪）。
  4. 项目验收有 fail 时 auditor 已写好修复项和担当模块，pm 只建修复模块任务（⑥ 轻）。立项评审的阻塞问题与模块过大共用 ≤2 次（①）。
  5. 结合测试：结合测试模块 agent 先确认是产品缺陷并写明担当模块（⑲），再上报调度（㉖ 轻）→ pm 建修复模块任务（㉓）→ 重新合并并重跑（㉔），≤2 轮后交用户（㉕）。
  6. W3 开发契约自包含；新增跨模块查询（靛蓝点划线，不计入返工）。
  7. 守护把无响应的 pm 移到「刷新」这条保留：进入时重置只清掉进入之前的历史，常驻步骤长时间停留仍会累积上下文，会话卡死也要靠它恢复。
  8. 缺口：结合测试缺陷的确认与归属由结合测试模块 agent（常驻「等待开发」实例）自己做，与规则 2 冲突——见方案 C。
方案 C = 方案 B + 下面各项。方案 C 不新增角色和步骤，只把机械性的工作从常驻会话移给脚本和一次性会话。
  1. C1 缺陷归属由发现它的测试任务完成（修正 B 的缺口）：结合测试任务在 defects 里直接写明担当模块和疑似位置，审核核对；结合测试模块 agent 只转交（⑲ 改为轻）。
  2. C2 路由备注规则（借鉴 dsh-superagent：主会话只转发原始内容加不超过 30 词的备注，不添加要求）：常驻会话下发修复时只给指向原修复项的指针和一句备注，不改写（㉓ 改为轻）。
  3. C3 合并门禁（借鉴 Anthropic C 编译器项目和 OpenAI harness：共享分支上的无回归门禁，机械强制优于文字规则）：「合并」在 rebase 后运行完整本地检查。失败直接退回「开发」（㉘，≤2 次），超过再升级模块 agent（㉙）。取代 ㉗。
  4. C4 合并下沉（借鉴 Cursor：去掉 integrator 角色，worker 自己处理合并）：门禁通过后「合并」步骤自己合入模块分支；模块 agent 不再合并，只在收到 REPORT 时放行后续任务。
  5. C5 契约检查脚本（借鉴 MAST：约 44% 的失败来自规格和系统设计；OpenAI：机械强制）：模块 agent 创建子任务前运行确定性脚本，检查 owns 不重叠、每个任务有 AC 和测试命令、每条跨模块边界都落到某个任务、依赖无环。
  6. C7 验收标准的覆盖核对（借鉴 Anthropic 长任务 harness：验收标准要明确、不可随意改动；MAST：验证只做表面检查是常见失败）：auditor 做模块验收时先核对 MA 是否覆盖模块契约的每条验收要点和相关的每条模块边界，有缺口即判不通过。不新增路径。
  7. C6 其余保留 B：知识分层、常驻步骤进入时重置、验收调查由 auditor 做、baseline 模块、跨模块查询；守护移到「刷新」同样保留。

设计来源不采用的原因
开工前由评审者和开发协商「完成的定义」（sprint contract）Anthropic 长任务 harness每个模块多一轮强模型会话；同一来源也指出评审环节只在任务超出模型能力时才值得，结构应逐项去掉非必要的；改用 C5 的脚本检查
常驻路由步骤换便宜模型，决策另开一次性会话Cursor / Anthropic 的按角色选模型剩下落在常驻会话上的都是需要判断的决策；要多加中转步骤，收益没有实测数据
无管理者的平级 agent + 锁文件Anthropic C 编译器依赖近乎完美的测试作为裁判，普通项目不具备
子 agent 之间共享完整对话记录Cognition 2025与减少上下文的目标相反；改用自包含契约和单写者
多 agent 辩论或投票多项研究显示不优于自一致性成本高，证据弱

相对方案 C 的主要差异
  1. 角色：新增 profile 键 plan_auditor（立项评审）、module（W2 模块规划 / 等待开发 / 刷新）、module_auditor（W2 验收调查）；auditor 只做项目验收。
  2. W1：立项评审第 3 次仍有阻塞 → 不论模式进「立项确认」交给人（㉚）；项目验收第 3 次仍有 fail → 列入「需要用户处理」提交人工终审（㉛）；调度中 ESCALATE / DECISION 影响到已完成的模块时，按修复模块任务创建（㉜）；集成分支的合并冲突写成修复项交 pm（只涉及共享文件的冲突就地解决，不算路径）。
  3. W2：验收调查有 fail 且进入次数 < 3 → 带修复项退回等待开发（⑩）；第 3 次 → 先升级 pm（⑪）；pm 接受为已知问题的项记 unverified，不再循环；模块只在两种情况下自己移到验收调查；拆分任务后原任务移到完成。* 「等待开发」从「验收调查」回来时发生 profile 切换，平台可能不执行重置，prompt 要求以 NOW 和文件为准。
  4. W3：开发上报 blocked / dropped / 结合测试缺陷后自己移到「等待决策」（不占并发名额），由模块 agent 移回开发或移到完成；合并 = 门禁 + 自己快进合入，门禁失败退回开发，第 3 次升级模块 agent；不再有 PR 方式；「待开发」任务不设平台依赖，由模块 agent 按 tasks.json 放行。
  5. 结合测试缺陷：测试任务写明担当模块（⑲）→ 结合测试模块只转交（㉖）→ pm 建修复模块任务（㉓）→ 修复完成后 pm 通知结合测试模块重新合并（㉔），测试任务移回开发重跑（㉝）。misrouted：修复模块带证据回报不归自己（㉞）→ pm 转给结合测试模块（㉟）→ 原测试任务重新判断（㊱），这一轮不计数。两轮仍不过 → attended 问用户（㉕）；unattended 写 ADR 接受为已知问题（㊲），测试用例标为预期失败后正常上报（㊳）。这组路径画在 W1 泳道右上角的小图里。
  6. 跨模块：有依赖的模块从依赖模块的分支切出；上游被修复后 pm 给下游进行中的模块发 NOTICE（Q4，通知类，不计返工）。
  7. 守护：pm 无响应只在「调度」触发，移到刷新时带返回步骤；W1 其他步骤空闲只写进给人看的 stage.md（G4，落点是用户）；「等待决策」停留过久告警模块 agent；会话失败由模块 agent 把任务移出再移回。
  8. 会话：调度、等待开发进入时重置；合并、收尾合并是 mechanical 新会话。

各版本对比

重 = 落点角色要自己调查、决策或重做；轻 = 拿到的是可直接下发的修复项，只需建任务或转交。常驻 = 「调度」「等待开发」这类长期停留的步骤。「新会话 / 入口」= 每次都是新会话的步骤数 / 入口步骤数（入口 = 立项规划、模块规划、开发：首次新会话，退回时沿用）。「调查由一次性会话完成」= 发现问题的源步骤是新会话，或是 W3「开发」这类一个任务一个会话的入口步骤（含结合测试任务等 W3 实例；开发任务结束后会话即弃用）；立项规划、模块规划虽是入口但会话长期沿用，不算。㉗、㉙ 的源步骤是「合并」新会话，但问题实际由模块 agent 处理，剔除。v3.2 之前的视图里，立项评审、项目验收、W2 验收调查都用 auditor（或 pm）profile，统计时按职能分别计入 plan_auditor / auditor / module_auditor 行；W2 的 pm 计入 module 行。
